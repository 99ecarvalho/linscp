linscp — Qt port of WinSCP

A cross-platform (Linux + Windows) Qt frontend over WinSCP’s protocol core, built so that upstream WinSCP remains trackable with near-zero merge cost.

Goal

One codebase. Qt UI. Builds and runs on Linux and Windows. No Embarcadero C++Builder in the toolchain.

Current state (2026-10-10)

Phase 0 under way — 7 of 18 tasks done. Upstream pinned as a submodule at 3rd-party/winscp — WinSCP 6.6.4-RC-3-gaaae9dcb5 (commit aaae9dcb, 2026-10-09).

Landed: the dual-target __property shim, the transformation script, and a compile-check harness. All 613 __property declarations in WinSCP’s core transform with zero unhandled cases and compile under clang. The keystone of the plan is no longer theoretical.

Next: core/Common.cpp against a minimal shim (P0-09) — the cheapest way to replace the Phase 1 estimate with a measurement.

The three findings the plan rests on

  1. __property is emulatable. clang supports __declspec(property) under -fms-extensions, verified on this machine (Debian clang 19) for every form WinSCP uses: field-backed r/o, field-backed r/w, method-backed with validating setter, read-modify-write, and indexed. GCC does not — clang is mandatory. WinSCP’s own compiler is already clang-based, so this is not a compiler-family change.

  2. Windows binaries can be produced on Linux. clang emits valid x86-64 COFF for both x86_64-w64-windows-gnu and x86_64-pc-windows-msvc, with property emulation intact. Verified locally.

  3. The de-VCL’d core already exists and is maintained. Far-NetBox (last commit 2026-07-24, tracking WinSCP 6.5.6 — one minor behind our pin) builds WinSCP core with MSVC/CMake over a hand-written ~16.3k-line VCL replacement in src/base/. It is Win32-targeted and its frontend is useless to us, but it is a proven reference for the hardest subsystem.

Non-negotiable constraints

  • Zero modified copies of WinSCP source in this repo. Core changes are produced by a committed, re-runnable transformation script plus a small patch series. See PLAN.md.
  • Transformations are line-preserving. Not an imposed constraint — all 613 core declarations are already single-line, so this costs nothing. The payoff is that diff -u upstream gen stays reviewable with zero offsets; it is asserted by a test rather than defended at any cost.
  • The C++Builder VCL build must stay green for as long as practical. This keeps upstream merges verifiable and keeps the door open with the maintainer.
  • CI builds Linux and Windows from the first commit. No “add Windows later”.

Plan

1. Answers to the four framing questions

Q1 — Can we compile the Windows version here on Linux and test it?

Two different questions, with two different answers.

Today’s VCL WinSCP: no. It requires Embarcadero C++Builder 11 (bcc64) plus MSBuild, the VCL runtime, and .dfm form compilation. The toolchain is Windows-only, proprietary, and has no cross-compiler. There is no path to building the current WinSCP.groupproj on Linux, and this will never change.

The Qt branch: yes. Verified on this machine:

clang++ --target=x86_64-w64-windows-gnu  -fms-extensions  -> x86-64 COFF  OK
clang++ --target=x86_64-pc-windows-msvc  -fms-extensions  -> x86-64 COFF  OK
clang++ --target=x86_64-pc-linux-gnu     -fms-extensions  -> ELF 64-bit   OK

All three with __declspec(property) emulation working. So one compiler (clang) covers all targets, which matters because GCC cannot compile the property shim at all.

Toolchain decision: clang + mingw-w64 (*-windows-gnu), not clang-cl. Rationale: no MSVC licence or xwin SDK download needed, a single libc++/libstdc++ story, and Debian ships the full mingw-w64 sysroot in apt. Keep the windows-msvc target as a later option if MSVC ABI interop is ever required.

Two real gaps, both solvable:

  • g++-mingw-w64 is in apt but is useless to us — GCC rejects __declspec(property). We need the mingw-w64 headers, libs and binutils and then drive them with clang++ --target=x86_64-w64-mingw32.
  • Qt6-for-mingw is not packaged in Debian. Cross-building the Qt GUI for Windows therefore needs Qt built once for mingw (a few hours, scriptable and cacheable in CI), or MXE. Phases 0–1 are unaffected — they have no Qt dependency, so cross-compilation works immediately for core and CLI.

Testing: Wine 10.0 is in apt. Good enough for CLI smoke tests and most Qt GUI behaviour. It is not sufficient to certify a Windows release — a real Windows CI runner is required before shipping binaries.

Q2 — A Qt branch that generates Windows builds and tracks upstream cheaply

See §3 Upstream tracking model. Short version: the port never contains a modified copy of WinSCP source. A committed script transforms the pinned submodule into a generated tree at build time.

Q3 — One codebase, Qt, both platforms

Endorsed as the end state, with one consequence worth stating plainly: Windows users lose the native-feeling VCL UI in exchange for a Qt one. That is the real cost of this project and the reason upstream would never undertake it. It also means C++Builder — a paid, proprietary, Windows-only compiler, and today the single largest barrier to outside contributors — leaves the toolchain entirely.

Q4 — “Shims get removed once the maintainer adopts it, and by then the UI must be 100% ported”

This is the one place the plan diverges from the brief. Three corrections.

(a) Most shims are not scaffolding — they are the permanent portability layer. The UnicodeString / TStrings / TDateTime shim is not a temporary adapter; it is the cross-platform RTL. Deleting it means replacing 5,178 UnicodeString and 497 TStrings uses across the core with std::wstring/QString and STL containers — a second project comparable in size to the first, with no user-visible benefit and a large regression risk. Recommendation: keep it permanently. A stable, well-tested 16k-line shim nobody has to look at is a feature, not debt.

What should eventually be deleted is different and much cheaper: the VCL frontend, the Windows-only Pascal packages, and the dual-target #ifdef __BORLANDC__ branches. That is Phase 4, and it is weeks of work.

(b) Do not couple cleanup to 100% UI parity. These are independent axes, and coupling them creates a trap: you would carry the dual-build burden for an extra year waiting on the last few preference dialogs. The correct trigger for retiring the VCL build is parity on the features users actually depend on, which lands well short of all 48 dialogs. Decoupling them also means a stall in UI work never blocks toolchain cleanup.

(c) Do not make an architectural decision contingent on a social outcome. The maintainer has publicly called a Qt rewrite an “inconceivable task”. Plan for this fork to stand alone and be sustainable indefinitely; treat upstream adoption as upside. The “keep the VCL build green” discipline in §3 is what maximises the chance of adoption — but the architecture must not depend on it.

2. Architecture

┌─────────────────────────────────────────────────────────────┐
│  qt/            Qt 6 frontend            (ours, new)        │
│  vcl-frontend/  existing VCL UI          (upstream, frozen) │
├─────────────────────────────────────────────────────────────┤
│  core/Interface.h — the frontend contract (upstream, as-is)  │
├─────────────────────────────────────────────────────────────┤
│  WinSCP core: SFTP SCP FTP WebDAV S3     (upstream, as-is)  │
│  PuTTY 0.85 · FileZilla FTP engine       (upstream, patched)│
├─────────────────────────────────────────────────────────────┤
│  port/shim/      VCL RTL replacement     (ours, permanent)  │
│  port/platform/  POSIX + Win32 helpers   (ours, permanent)  │
├─────────────────────────────────────────────────────────────┤
│  OpenSSL · expat · neon · libs3          (system packages)  │
└─────────────────────────────────────────────────────────────┘

core/Interface.h already is a clean abstract frontend contract — free functions and virtuals (ShowExtendedException, CopyToClipboard, ProcessGUI, CreateConfiguration, StartThread). The core never calls the GUI directly. ProcessGUI is virtual on TSessionUI, so a headless frontend no-ops it. Config storage is already abstracted behind THierarchicalStorage with both registry and INI backends; Linux uses the INI path. We are filling in an existing seam, not cutting a new one.

The dual-target macro — the keystone of the whole plan

The __property rewrite expands to native VCL syntax on C++Builder and to __declspec(property) everywhere else:

#ifdef __BORLANDC__
  #define PROP_RW_GS(T, Name, G, S) __property T Name = { read = G, write = S }
#else
  #define PROP_RW_GS(T, Name, G, S) __declspec(property(get=G, put=S)) T Name
#endif

This makes the transformation non-destructive: the same transformed header compiles under C++Builder and under clang. That single property is what lets the VCL build stay green, what makes the diff theoretically acceptable upstream, and what keeps the port honest.

Property forms in core, all mechanically rewritable:

Form Count
read = FField 576
write = SetX 362
read = GetX 246
write = FField 182
index = … (4 hand-written wrappers) 4
default / nodefault / stored 0

591 declarations across core headers; four exceptions. Everything else is a one-line-in, one-line-out substitution.

Other Embarcadero extensions: __fastcall (5,277 sites) becomes an empty #define — zero diff. __closure (45 sites) becomes a macro over a std::function-alike. ARRAYOFCONST (29) needs a variadic shim. Delphi Set<> appears once in core.

Win32 call sites in core

Roughly 200 direct Win32 calls across ~40 distinct functions (CreateFile, ReadFile, GetFileAttributes, FindFirstFile, WSAEventSelect, CreateEvent, one RegQueryValueEx, one SHGetFolderPath). Rather than edit core, implement that subset in port/platform/win32-on-posix/. This keeps the core diff at zero at the cost of a contained, well-understood compatibility module. WSAEventSelect semantics are the awkward part; everything else is routine.

Stored-password crypto is not DPAPI — core uses its own Cryptography.cpp, so it ports cleanly.

3. Upstream tracking model

Generated-tree model. This repo contains zero modified WinSCP source.

linscp/
├── 3rd-party/winscp/      submodule, pristine upstream, pinned to a tag
├── port/
│   ├── tools/transform.py committed, re-runnable, line-preserving
│   ├── patches/*.patch    small series for what cannot be mechanised
│   ├── shim/              VCL RTL replacement        (first-class source)
│   └── platform/          POSIX + Win32-on-POSIX     (first-class source)
├── qt/                    Qt 6 frontend              (first-class source)
├── cmake/
└── build/gen/             generated transformed tree (gitignored)

Build = transform.py reads the submodule → writes build/gen/ → compile build/gen/ + port/ + qt/.

Updating to a new WinSCP release:

  1. git -C 3rd-party/winscp fetch && checkout <new tag>
  2. Re-run transform.py
  3. Re-apply the patch series; fix rejects
  4. CI runs the golden-output suite on Linux + Windows

Your diff against upstream is structurally empty, so there is nothing to conflict. The maintenance burden is the script and the patch series, not 77k lines of forked code. Anything the script cannot express mechanically is a deliberate decision recorded as a patch — which keeps the patch series small by construction, because a growing series is an immediate, visible warning sign.

This is exactly what the submodule you asked for is good for: a pristine upstream reference, not a vendored copy to edit.

Branches

Branch Role
main the port: port/, qt/, doc/, submodule pin
upstream-pin/* tags recording which WinSCP commit each release was built against

No long-lived divergent branch is needed, because there is no forked source to diverge. This is the structural reason to prefer this model over forking winscp/winscp outright.

4. Incremental UI strategy

Do not mix VCL and Qt in one process. It is technically possible on Windows and a maintenance disaster, and it is impossible on Linux where VCL does not exist. “Incremental” must mean something else.

The workable model: two independent frontends over one ported core.

  • vcl-frontend/ — the existing UI, untouched, builds only on Windows with C++Builder. Stays shippable throughout.
  • qt/ — starts minimal and grows feature by feature on both platforms.

The Qt app becomes the default when it is good enough; the VCL build is retired in Phase 4. Users are never handed a half-ported UI, and UI work can stop and restart at any point without breaking anything.

The .dfm designer files are an asset here, not an obstacle: each is a declarative spec of a dialog’s layout, widgets, captions and tab order, which makes .dfm → .ui conversion unusually tractable and reviewable.

The 121k lines of Pascal component packages are deleted, not ported — all seven map onto functionality Qt already ships:

Deleted Replaced by
Toolbar2000 + TBX (32k) QToolBar / QMenuBar
filemng shell tree (14k) QFileSystemModel
JCL (59k) utility code; drop
PngComponents (4.6k) Qt native image support
dragndrop (3.6k) Qt native drag & drop

Translations in translations/ should be reused rather than rewritten; mapping WinSCP’s string tables onto Qt’s tr()/.ts pipeline is a task in its own right (P3-07) and is worth doing early enough to avoid hardcoded strings accumulating.

5. Verification strategy

The thing that makes this port tractable to verify, not just write:

Golden-output differential testing. WinSCP’s scripting frontend emits deterministic XML session logs — the same protocol the netstandard2.0 .NET assembly already consumes. So:

  1. Build a corpus of scripts covering SFTP/SCP/FTP/FTPS/WebDAV/S3 operations.
  2. Run each against real WinSCP on Windows → golden XML.
  3. Run each against the port → candidate XML.
  4. Normalise (timestamps, paths, session IDs) and diff.

This gives a regression suite over the core port for a fraction of the cost of writing unit tests for 77k lines, and it is the single highest-leverage item in Phase 0. Protocol servers come from containers (OpenSSH, vsftpd, ProFTPD, Apache/WebDAV, MinIO) so the matrix runs in CI.

Corollary benefit: the existing .NET assembly targets netstandard2.0 already, so it will drive the Linux port unchanged once the CLI speaks the same protocol.

6. Risks

# Risk Severity Mitigation
R1 C++Builder rejects __property produced by macro expansion, killing the dual-target keystone High Cheap to test — one header, one person with a licence, Phase 0. Macros expand before parsing and bcc64 is clang-based, so confidence is high but it is unverified here. If it fails, the VCL build cannot stay green and §3’s upstream story weakens considerably. Test this first.
R2 FileZilla WSAAsyncSelect → epoll rewrite introduces subtle async bugs High ~1,700 lines of hidden-window message-pump state machine. Golden-output suite + a real FTP server zoo. Budget generously; this is the least mechanical task in Phase 1.
R3 No C++Builder licence and no Windows machine available locally Medium Windows CI runner; R1 needs a collaborator or a trial licence
R4 Qt6-for-mingw not packaged; must be built once Medium Scripted, cached CI artifact; blocks only Phase 2+
R5 Qt UI parity is the dominant cost and may stall Medium Decouple from Phase 4 per Q4(b); ship a useful subset early
R6 WSAEventSelect emulation on POSIX proves awkward Medium Core’s socket use is mostly mediated by PuTTY/FileZilla; scope is small
R7 Upstream churn outpaces the transform script Low Script is declarative and line-preserving; patch-series growth is the early-warning signal
R8 Protocol regressions reach users Medium Golden suite is a merge gate, not an afterthought

R1 is the project’s pivot point. Everything in §3 — the zero-diff upstream story, the green VCL build, the plausible path to maintainer adoption — rests on it. It is also among the cheapest things to test. Do it first, before any shim code is written.

Estimates

Assumptions

  • Human baseline: one senior C++ developer, full-time, familiar with Qt and cross-platform build systems, but not initially familiar with this codebase.
  • AI-assisted: the same developer driving Opus 5 as the primary implementer, reviewing everything that lands.
  • Calendar months, full-time. Includes code review, debugging and testing — not just first-draft authoring.
  • Access to a Windows CI runner and containerised protocol servers.
  • Excludes project management, release engineering, docs for end users, and community/maintainer negotiation.

Where AI actually multiplies — and where it does not

The multiplier is highly uneven across this project, and the uneven parts are what the estimate turns on.

Strong fit (3–8×)

Work Why
transform.py (P0-05/06) Mechanical, 4 regular forms, immediately self-testable by re-running
VCL RTL shim (P1-01…06) Well-specified APIs, a maintained reference to crib from (Far-NetBox src/base/), and unit-testable in isolation. The single largest chunk of P1 is also the best-suited
win32-on-posix (P1-07) ~40 functions with precise documented semantics
CMake / CI / toolchain files (P0-08…12) High boilerplate, fast feedback
PuTTY unix/ re-import (P1-09) Mostly reconciling two known trees
.dfm → .ui + dialog port (P3-01/04/06) .dfm is a declarative spec of layout, widgets, captions and tab order. This is the biggest single AI win in the project, and it sits in the most expensive phase

Moderate fit (1.5–2.5×)

Work Why
Qt Interface.h implementation, file panels, queue UI (P2-03…08) Real interaction logic and design judgment; AI drafts well, polish is human
Commander dual-pane semantics (P3-02) Deep keyboard-driven interaction behaviour users will notice immediately
First successful link (P1-17) AI is excellent per-fix, but the iteration count is high and each cycle is gated on a working build

Weak fit (1–1.5×)

Work Why
FileZilla epoll rewrite (P1-12) ~1,700 lines of subtle async state machine. Correctness is established by testing against real servers, not by reading code. Verification-bound
Protocol correctness (P0-15, P1-19) The FTP server zoo, SFTP extension quirks, S3 and WebDAV edge cases. Wall-clock bound by test infrastructure and real-world behaviour
C++Builder / Windows-native tasks (P0-04, P0-15) No local access; bound on a collaborator or licence
UX parity judgment Deciding what “parity” means is not a code task

The binding constraint

Code generation is not the bottleneck; human review and real-world verification throughput are.

This matters for planning:

  • Compute cost is not the limiter. Reviewer attention is. A reviewer who merges a 4,000-line shim without reading it has converted a 3× multiplier into a latent defect fund.
  • The highest-leverage investment is therefore P0-13/14 (the golden-output harness and server containers). It raises the trustworthy review rate for every phase that follows. Underfunding it caps the achievable multiplier for the whole project, which is why it sits in Phase 0 rather than “later”.
  • Phases whose cost is dominated by testing against reality (P1-12, P1-19) barely move with AI. Do not plan as though they will.

Sensitivity

The estimate is dominated by one undecided question.

Variable Effect
P3 scope (Q-1) A deliberately narrower Qt client cuts P3 from 6–12 to ~3–5 months → total 8–14 months. This is the single largest lever in the plan
R1 fails (C++Builder rejects the macro) P0 +0.5 mo, and the zero-diff upstream story weakens — higher ongoing merge cost, not a higher build cost
R2 worse than expected (FileZilla rewrite) P1 +1–2 mo. Mitigation: ship SFTP/SCP/S3/WebDAV first and treat FTP as a later deliverable
No Windows host available P0-04 and P0-15 stay blocked; the dual-target guarantee becomes unverified and Windows releases cannot be certified

Honest caveats

  • These numbers come from static analysis only. Nothing here has been built. Line counts, grep results and the two compiler experiments are solid; the estimates derived from them are judgment.
  • The usual failure mode for ports of this shape is a long tail of small incompatibilities discovered only at link and run time (P1-17). The P1 range is wide for that reason, and it is the range most likely to be exceeded.
  • P0-09 is the cheapest way to replace guesswork with measurement. Compiling one real core translation unit against a minimal shim will tell us more about the P1 estimate than any further analysis, and it is roughly a week of work.
