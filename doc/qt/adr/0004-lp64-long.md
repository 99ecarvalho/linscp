# ADR 0004 — Core's `long` stays 32 bits on LP64

**Status:** accepted 2026-10-11
**Date:** 2026-10-11 (recorded 2026-10-12)

## Context

Windows is LLP64: `long` is 32 bits, Win64 included, so WinSCP's own 64-bit
port never meets this. Linux x86-64 is LP64. Core relies on 32-bit `long`:
`TSFTPPacket` read and wrote `sizeof(unsigned long)` bytes per SFTP uint32 --
8 on Linux -- and sign-extends 32-bit times through `signed long`. The first
Linux SFTP session misparsed the server's version packet.

## Options

**A. Patch each site.** A long tail, and the failures are silent misreads.

**B. A transform rule.** Respell core's `long` as `LONG` and `unsigned long`
as `ULONG`: `<windows.h>`'s typedefs of exactly those types, so C++Builder
and mingw see no change, and 32 bits in the POSIX layer.

## Decision

**Option B**, the `lp64_long` rule in `transform.py`, core files only;
comments, literals, `long long` and `long double` untouched. Lines where core
implements another library's interface keep `long`
(`port/tools/lp64_long_keep.txt`); a missing entry is a conflicting-declaration
error, not a silent one. `verify_transform.py` checks the rule with its own
token-based implementation. The shim's `%l` and `swscanf`'s `%l` are 32 bits,
Windows' meaning.

## Consequences

- Upstream's meaning everywhere at once; PuTTY (LP64-clean) and FileZilla are
  not rewritten.
- New upstream code using `long` for 32 bits is covered automatically; new
  code implementing a library callback with `long` fails to compile until
  listed.

## Verification

`lp64_long` (rule tests), `transform_verify`, and every SFTP session on Linux.
No core override hides a virtual (checked with `-Woverloaded-virtual`).
